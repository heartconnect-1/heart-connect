# Heart Connect Security Stabilization Tests — 2026-09-10

## Test 1 - Private profile media is enforced by every discovery API
Viewport: desktop (1280x800)
Covers: /api/discover, /api/stage4/home, /api/stage4/explore, /api/stage4/profile/:id, /api/stage4/connections, photoVisibility, showTravel
Setup:
1. Actor A and Actor B are authenticated adult members with profile photos, video and voice media.
2. Actor B sets Photo visibility to Private and disables Show Travel.
Steps:
1. Actor A loads Discover, Explore and Actor B's profile.
2. Inspect API payloads as well as visible UI.
3. Confirm Actor B's photos, video and voice URLs are absent and travel data is absent.
4. Change Actor B to Photo visibility = Mutual matches only while the pair is not matched; repeat.
5. Make the pair a true mutual match and repeat.
Expected: Private media is never signed or returned. Match-only media is returned only after both profiles like each other. Travel data follows the target member's privacy setting.

## Test 2 - One-way likes cannot message, call or subscribe to conversation realtime
Viewport: mobile (375x667)
Covers: messaging-core mutual authorization, advanced calls, realtime subscriptions, Stage 5 profile actions
Setup:
1. Actor A likes Actor B. Actor B has not liked Actor A.
Steps:
1. As Actor A, open Actor B's profile and confirm Message/Audio/Video actions remain locked.
2. Attempt GET and POST messaging endpoints for Actor B directly; expect 403.
3. Attempt to start an audio/video call; expect 403.
4. Attempt to subscribe to pair conversation realtime; expect 403.
5. Actor B now likes Actor A. Repeat all eligible actions.
Expected: One-way interest never opens communication. Messaging, calls and realtime conversation subscriptions become available only after a true mutual match.

## Test 3 - Realtime subscriptions are owner-scoped and deduplicated
Viewport: desktop (1280x800)
Covers: /api/subscriptions, /api/subscriptions/remove, route precedence, user/conversation/call authorization
Steps:
1. Subscribe Actor A to Actor A's own user channel twice using the same connection ID.
2. Confirm only one effective subscription record exists.
3. Attempt to subscribe Actor A to Actor B's user channel; expect 403.
4. Attempt to remove Actor B's subscription using Actor A's session and connection parameters; expect denial/no cross-user deletion.
5. Verify the effective route is the hardened realtimeSubscriptionRoutes implementation, not the older Stage 3 duplicate.
Expected: Subscriptions cannot be claimed or removed across users, conversation subscriptions require mutual matches, and duplicate subscriptions are not accumulated.
